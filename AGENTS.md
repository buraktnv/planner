# AGENTS.md — Planner

Local-first planner web app: tracks dev projects and life areas via markdown + git, surfaces "what to do next and why", and integrates AI (web chat with tool calls, MCP server for coding agents).

Spec: `docs/superpowers/specs/2026-08-27-planner-design.md`

## Two-repo layout

- This repo (`planner`): app code only. It **is public**, MIT licensed — **never commit personal data here**. Test fixtures and doc examples use `acme-*` placeholder slugs; if a real project or person name appears in a diff, it is a bug. Note that git history is public too, so a leak cannot be fixed by a later commit.
- `planner-data` repo: all user data (markdown). Path configured via `PLANNER_DATA_DIR` env var (default `../planner-data`). Git auto-commits happen there, not here.

## Commands

```bash
npm run dev          # dev server on :3000
npm run build        # production build
npm run lint         # next lint
npm run typecheck    # tsc --noEmit
npm test             # vitest run (all tests)
npm run mcp          # stdio MCP server for coding agents (see docs/mcp.md)
npx vitest run lib/core/schema.test.ts   # single test file
```

All of `lint`, `typecheck`, `test` must pass before considering any change done.

## How agents are told to use the planner

Two layers, on purpose.

- **`mcp/instructions.ts`** — handed to every MCP client on connect, so an agent
  gets the standing rules without anyone pasting them. Deliberately short: these
  sit in context for the whole session, so only what an agent gets *wrong by
  default* belongs here — filing a duplicate note, re-deciding something already
  settled, creating a task attached to nothing, trying to write a charter no tool
  can write. `mcp/__tests__/instructions.test.ts` caps the length and asserts it
  never cites a tool the allowlist does not expose.
  It now carries a fifth standing rule — *record the wrong turns* — because
  an agent's default is to try something, fail, move on and leave no trace.
  It was paid for by tightening three paragraphs rather than raising the cap;
  the file sits within a few characters of the limit, so anything added here
  has to buy its space the same way.
- **`.claude/skills/planner-sync/SKILL.md`** — the procedure, loaded only when
  the task calls for it: audit before sync, read note *bodies* before deciding,
  hand back charter text no tool can write, attach every task to a target or a
  component. Anything long or situational goes here rather than into the
  always-on instructions.

`.gitignore` tracks `.claude/skills/` and ignores the rest of `.claude/` —
worktrees and machine-local settings must never be committed.

Note the asymmetry the instructions exist to explain: **the app's own chat can
create charters directly; an MCP agent may only propose one.**
`create_project` / `create_area` are `OWNER_ONLY_TOOLS` in `mcp/allowlist.ts`
and absent from `allowedToolNames`, while the chat route registers every schema
in `lib/ai/schemas.ts`. They are *also* members of `proposalActionSchema`, which
is what lets an agent put a charter in a `propose_changes` batch for the owner
to accept — proposable, never callable, and `mcp/__tests__/server.test.ts` pins
both halves of that sentence.

The log tools sit deliberately on the other side of that line: `add_task_comment` is a plain `WRITE_TOOLS` member and **not** a `proposalActionSchema` member, because an entry records what already happened rather than proposing a change. Routing it through review would mean the record is only made if the owner clicks Accept — and the entries most likely to be discarded are the dead ends, which are the ones worth keeping most.

The reason it is a proposal rather than a write: *no* surface has a
charter-*edit* tool at all, so a Why, an MVP scope or a target can only be
changed by a human in the UI. The review modal is therefore the **last** moment
a charter's thinking can be corrected, which is why `fieldsForKind` gives both
kinds real textarea fields rather than a read-only preview row.

## The working loop

Four beats, in this order, for any piece of work — on a project the planner
tracks, and on this repo itself. Each one leaves a record the next can be
checked against, which is the only reason the order matters.

1. **Write the idea down before deciding whether to do it.** A new idea gets a
   file the moment it exists: a knowledge note in the data repo (`add_note`),
   or a spec under `docs/superpowers/specs/` when it is a change to the planner
   itself. This holds **even when nothing is being scheduled**, and that case is
   the point of the rule rather than an exception to it — work that becomes a
   task is at least visible on a board, so the idea actually at risk of being
   lost is the one nobody is acting on yet.
2. **Create the task with its description, before starting.** `create_task`
   takes a `description` and the New Task dialog has a box for it above STEPS,
   so there is no moment where writing it costs a second round trip. Written
   first it is a plan; written afterwards it is a summary of what happened,
   which is a different and much weaker document.
3. **If it needs splitting, say why those are the pieces.** `decompose_task`
   takes a `reason`, filed as the first comment on the parent. The subtasks
   record *what* the pieces are; nothing else records why the work divides
   there, so a later reader cannot tell a considered split from an arbitrary one.
4. **Log as you go, and log the wrong turns first.** `add_task_comment` appends
   to `<slug>/comments/<task-id>.md`; nothing in the app edits or deletes an
   entry. The moment to write one is when an approach is abandoned, not when the
   work lands — a record that only survives if it turned out well is not a
   record of the work, and the dead end gets walked again next month.

The split between the two free-text fields is what makes this work at all. The
**description** is one document that is overwritten, so it always reads as the
current plan; the **log** is append-only, so it keeps what was thought before.
Neither can do the other's job, which is why a wrong turn is never "fixed" by
editing the description — doing that destroys the only copy of the reasoning
that the next person needs.

This loop is carried in two places on purpose, along the same seam as *How
agents are told to use the planner* above: `mcp/instructions.ts` states it as a
standing rule, so an MCP agent
follows it without being asked, and `.claude/skills/planner-sync/SKILL.md`
carries the long form for when the procedure is actually being run. A change to
the loop that lands in only one of them puts agents and humans on different
rules.

## Architecture rules (non-negotiable)

1. **All data access goes through `lib/core`.** No other code reads or writes the data directory. `app/` routes and components call `lib/core` functions. The future MCP server will wrap `lib/core` too — keep it the single gateway.
2. **AI tools call `lib/core` only.** Tool definitions live near the chat route but their implementations delegate to `lib/core`.
3. **Data root comes from `PLANNER_DATA_DIR`** (resolved in one place in `lib/core`). No hardcoded paths to the data repo.
4. **Secrets only in `.env.local`** (never committed, never written into data files). Provider profiles reference env var names via `apiKeyEnv`, not raw keys.
5. **Every data mutation** goes through `lib/core` write functions, which append a journal entry and git-commit in the data repo. Do not bypass.
6. Test fixtures use generic fake data, never real personal data.

## Data schema quick reference

- Charter files (`projects/<slug>.md`, `areas/<slug>.md`): YAML frontmatter (`id`, `name`, `type`, `status`, `priority`, `mvp`, `repo`, `created`, `updated`) + body sections `## Why`, `## MVP scope`, `## Parking lot`
- Task lines (fixed grammar, parsed by `lib/core/schema.ts`):
  `- [ ] T-007 | M | Title | created:2026-08-27`, subtasks indented with dotted ids (`T-007.1`), done: `- [x] ... | done:2026-08-27`; sections `## Backlog` / `## In progress` / `## Done`
- Optional field keys after the title: `created:` / `est:` / `due:` / `lane:` / `target:` / `waits:` / `done:`
- **A title may not contain `" | "`.** It is the third delimited field of a closed grammar, so a title carrying the delimiter parses back as an extra field and `parseTasks` throws — and because `serializeTasks` rewrites the whole file, that makes *every* task in the charter unreadable, not just the bad line. `cleanTitle` in `lib/core/store.ts` rejects it at the writer, the way `calendar.ts` has always guarded event titles; nothing downstream escapes or repairs it, because a title that has already been written is too late.
- `lane:` is one of `quick` | `deep` | `wait` | `some` — the Board's four columns. It is optional; when absent `laneOf()` in `lib/core/lanes.ts` derives it (size `S` → quick, otherwise deep). Dragging a card on the Board writes this field.
- `target:` links a task to a charter goal (`target:G-001`). Targets live in the **charter**, not in `tasks.md`, so `parseTasks` validates the *shape* only (`/^G-\d{3,}$/`) and tolerates an id that does not exist — validating existence would let a charter edit make a task file unparseable, and unknown keys are already fatal. Resolution happens in the view layer, where an unknown id simply shows no link. Serialized between `lane:` and `waits:`.
- **Targets and milestones** live inside a charter's `## MVP scope`, which the charter parser treats as an opaque `string[]` and re-emits verbatim — so this needed no schema change. A target line is `- [ ] G-001 | Title — by 30 SEP`; a `### M1 — name` heading above it groups the targets beneath into a milestone. `lib/view/targets.ts` owns all of it: `parseTargetLine` reads an optional `G-nnn | ` prefix (a line without one still parses, it just cannot be linked), `milestonesOf` groups in document order, `nextTargetId` mints from the highest id present, and `targetProgress` computes `done/total` over the tasks naming that id, falling back to the tick when none are linked. A target is never auto-closed when its tasks finish. **`Target.index` is the index into the raw `mvpScope` array** — `toggledScope` writes by it, so headings must occupy slots without being renumbered. `targetsOf` must never throw: it runs inside `loadWorkspace`, where an exception takes down every page. `/targets` renders this as the Roadmap.
- `waits:` is a dependency: either a task id in the **same file** (`waits:T-041`) or free text without ` | ` (`waits:the clinic`). Serialized after `lane:`. An unknown id is tolerated by the parser; `isBlocked()` in `lib/core/deps.ts` then treats it as free text. A done blocker unblocks automatically. Blocked tasks sink to the bottom of the Focus ranking and are never the One Thing.
- A subtask and its parent may sit in **different sections** (completing a subtask moves only that line to `## Done`). The parser resolves parents by dotted id across the whole file, not by position.
- Task detail (`projects/<slug>/details/<task-id>.md`, same for `areas`): the plan behind one task or subtask — free markdown, **no frontmatter and no parser**, read and written by `lib/core/details.ts`. The task line grammar is closed (six keys, `" | "`-delimited, unknown key is a fatal error, `serializeTasks` rewrites the whole file), so detail deliberately lives outside `tasks.md` where it can never corrupt it. The filename carries the id, including dotted subtask ids (`T-007.2.md`). `taskId` is validated against `/^T-\d+(\.\d+)*$/` before it is ever interpolated into a path — it arrives from HTTP routes and AI tools, so this guard is the only thing standing between a caller and the filesystem. Writes go through `withDataLock`, journal, and commit. Because `archiveCharter` renames the whole `<slug>/` directory, details archive and restore with their charter. `listDetailIds()` feeds the `hasDetail` flag on `CardModel`/`SubModel`. **On screen this is the DESCRIPTION**, and "detail" is only the internal name — the directory, the module, `hasDetail` and the `read_task_detail`/`write_task_detail` tools all keep it, because renaming them would churn every data file and the MCP surface for a label. It is written at capture time too: `POST .../tasks` takes an optional `description`, and `createTask` takes one as well. It is a **single document that is overwritten** — `write_task_detail` replaces it wholesale — which is exactly why a wrong turn belongs in the log below and not here, and why the log could not live inside this file: the description editor PUTs the whole body, so a log kept here would be destroyed by the next save.
- Task log (`projects/<slug>/comments/<task-id>.md`, same for `areas`): the **append-only** record of what actually happened while the work was done, written by `lib/core/comments.ts`. One entry is a stamp heading plus free markdown: `## 2026-09-01 14:22` then the body, running to the next stamp — so an entry is multi-line and a pasted stack trace or fenced block survives verbatim. A line is only an entry boundary if it matches the stamp shape exactly, so a body containing `## Results` cannot split itself; and `serializeComment` **indents a body line that does match**, at the writer, the way `cleanTitle` guards `" | "` — a body already on disk is too late. `parseComments` is **total, it never throws**, in the manner of `parseCanvas`: this file is appended by two OS processes *and* hand-edited, and it renders inside a page that must not fall over, so text before the first stamp is kept as `preamble` and an unrecognised `· marker` round-trips rather than being eaten — which is what lets entry *kinds* be added later without migrating a file. `appendComment` only ever `appendFile`s, so unlike every other writer here there is no read-modify-write window at all and a torn write costs the entry it cut, never the file; `lib/core/__tests__/concurrency.test.ts` races two of them to prove it. It still takes `withDataLock` once, journals `<id> comment added` and commits. Entries have **no ids and nothing edits or deletes one** — there is no PUT and no DELETE on the route, because a log you can launder is the failure this replaces; a genuine mistake is fixed by hand in the markdown, with a diff. Empty bodies and bodies over 10 000 characters are refused. It archives and restores with its charter for the same reason `details/` does.
- `archive/projects/<slug>.md` + `archive/projects/<slug>/` (same for `areas`): where `archiveCharter()` moves a charter and its tasks dir. Nothing is ever hard-deleted; the parser never reads `archive/`. Collisions get a `-2`, `-3`, … suffix. Read back — opt-in only, never by `listCharters` — via `listArchived()` / `getArchived()` / `listArchivedTasks()`, and reversed by `restoreCharter()`. An archived charter's frontmatter is **not** rewritten, so it still says `status: active` and keeps its original `id`; living in `archive/` is the only trustworthy archived signal. `restoreCharter` reuses the archiver's collision loop and, when the original slug is occupied, lands on `-2` **and rewrites the frontmatter `id` to match** — two live charters sharing an id would collide in the workspace map and the sidebar. The `/archive` page browses and restores; archiving and restoring are deliberately absent from the AI tools and the MCP allowlist.
- Calendar: `calendar.md` at the data root, no sections, one event per line, kept sorted by date then time on write:
  `- [ ] E-001 | 2026-09-01 | Passport appointment | time:09:40 | note:bring photos | scope:area:admin | action:photos not printed`
  Fixed order is checkbox, id (`E-` + 3+ digits, monotonic), ISO date, title, then optional `time:` (free, ≤ 12 chars) / `note:` / `scope:` (`<project-slug>` or `area:<slug>`) / `action:` (free text = what still needs doing) / `repeat:` (`yearly` | `monthly` | `weekly`) / `lead:` (`21d`, 1–999). Parsed by `lib/core/calendar.ts`; `action:` present on an open event is the "needs action" flag.
  **The date is an anchor, and the file never depends on today.** `lib/core/recurrence.ts` is pure and derives `nextOccurrence` / `occurrencesBetween` / `isSurfaced` at read time, so a repeating event sorts by the date it was written with. Ticking a repeating event **advances the anchor and leaves it open** rather than closing it — a handled birthday otherwise sits in TODAY all day — which also means the birth year belongs in `note:`. `lead:` is the number of days before an occurrence that the event belongs on Today, under COMING UP and in chat context; "photoshoot before the passport appointment" is one event with `action:` + `lead:21d`, never a task, because a task with `due:` would say the same thing in two files and need two ticks.
- `daily/`: four definition files plus one append-only log, parsed by `lib/core/daily.ts`:
  `daily/habits.md` `- H-001 | Walk | goal:4 | unit:× 15 min` (goal is per day, `unit:` optional) · `daily/rhythms.md` `- R-001 | Laundry | per:3` (times per week) · `daily/meals.md` `- M-001 | Lentil soup | servings:2` (live remaining count) · `daily/groceries.md` `- [ ] G-001 | Red lentils | cat:Staples` · `daily/log.md` `- 2026-08-28 09:12 | H-001 | +1` where the delta is `+n`, `-n` or `reset`.
  Ids are `H-`/`R-`/`M-`/`G-` + 3+ digits, monotonic per file. A habit's count for a day and a rhythm's count for the Mon–Sun ISO week are summed from the log, restarting after each `reset`; tapping a row that already meets its goal appends `reset` (wrap-around). Eating a meal decrements `servings:` in place and appends a `-1` log line. `lib/view/daily.ts` builds the `/daily` screen model.
- Knowledge base (`knowledge/`): one note per file, `knowledge/<id>-<title-slug>.md`, parsed by `lib/core/knowledge.ts`. YAML frontmatter `id` (`K-` + 3+ digits, monotonic), `title`, `summary` (single line — the only text ever auto-loaded), optional `scope` (list of project slugs or `area:<slug>`) and `tags` (lowercase slugs), `created`, `updated`, optional `source`; body is free markdown with `[[K-009]]` links. Unknown frontmatter keys are a parse error. The filename is fixed at creation so links never break when a title changes. `knowledge/index.md` is **generated** derived state — one `id | scope | tags | title | summary` line per note, rebuilt on every write, never read as truth. Retrieval is three-tier: `buildSystemContext` loads index lines for the focused scope only (cap 40), `search_knowledge` ranks all notes (title 8 / tags 6 / summary 4 / body 1, capped at 5), `read_note` returns one body plus backlinks. Scopeless notes are searchable but never auto-loaded. Notes filed without a `scope` are categorised automatically by `lib/ai/classify.ts` (AI layer, never `lib/core`): a literal charter slug/name in the text wins for free, otherwise a structured-output model picks one existing scope from a closed list, or proposes a new area. `normaliseScope` repairs and then *rejects* anything not in that list, so an invented scope can never reach the writer. When nothing fits, `createAreaGuarded` may mint one area — refused for generic names (`NEVER_MINT`), slug collisions, near-duplicates, notes too short, or when a week's budget is spent; each mint journals `area auto-created`. `lib/ai/file-note.ts` is the single write path for AI-filed notes (dedupe via `nearDuplicateOf`, daily cap, then `addNote`). `buildSystemContext` takes a third `query` argument — the latest user message, extracted server-side by `lib/ai/recall.ts` — and `knowledgeSection` uses it to surface relevant notes even with no focus; it never returns zero titles. **Every** `lib/core` write is serialised by `lib/core/locks.ts` (in-process chain + a cross-process `mkdir` lock in the OS temp dir), because the MCP server is a separate process and duplicate ids brick `listNotes`. This sentence used to say "note and charter writes" and was wrong: `store.ts`, `calendar.ts` and `daily.ts` took no lock at all, and since every writer reads the file, mints an id and rewrites the **whole** file, two interleaved writes did not merely collide on an id — the second silently clobbered the first, so a task the user had just created vanished with no error. `lib/core/__tests__/concurrency.test.ts` races real writers and is the only place that failure is visible; every single-writer test passed either way. Two things to know before touching this: `withDataLock` is **not re-entrant** (it chains on one module-level tail, so a locked function calling another locked function deadlocks — which is why `logDaily` stays a plain delegator to the locked `logHabit`/`logRhythm`, and why the wrappers call an unlocked inner `…Unlocked` function rather than each other; the same rule is why anything that creates a task *and* writes a description or a comment must **sequence** them — `await addTask(…)` then `await writeDetail(…)` or `await appendComment(…)`, never nested — which `createTask`, `decomposeTask` and both task `POST` routes all depend on), and the holder **heartbeats** the lock's mtime, because staleness otherwise measures when the lock was *taken* and a slow-but-alive `git add -A` would have its lock stolen. `MAX_WAIT_MS` must therefore stay well above `STALE_MS`, or a waiter gives up before it can ever reach the takeover it is waiting for.

Per-charter docs are the same notes, surfaced per scope. `/projects/<slug>/docs` and `/areas/<slug>/docs` render every note scoped to that charter, grouped by the note's **first** tag (`lib/view/docs.ts`, `PREFERRED_TAGS` = architecture, protocol, decision, runbook, reference; everything else alphabetical; untagged last under "Unfiled"). There is deliberately no second markdown store for documentation and no page tree: a project's docs *are* its scoped notes, so they inherit search, `[[K-009]]` links, AI auto-load and the MCP tools for free. The consequence to know: notes live in `knowledge/`, so they do **not** archive with a charter. `buildDocs` is pure and takes the already-loaded note list; the pages call `getCharter` rather than `loadCharterModel`, which would load the whole workspace to read one name.

Journal distillation (`lib/ai/distill.ts`, `POST /api/knowledge/distill`) turns journal entries into *proposed* notes through the existing `propose_changes` → Accept/Discard card; `add_note` / `update_note` are proposal action kinds, so chat can batch them too. It needs a structured-output provider — the `claude-subscription` path is chat-only. Spec: `docs/superpowers/specs/2026-08-28-knowledge-base.md`
- **Images** (`assets/`): the only binaries in the data repo. Flat directory, **content-addressed** names (`sha256(bytes).slice(0,16) + ext`), referenced from note markdown as `![alt](assets/<name>.png)` — a repo-relative path, so the note still reads correctly in a plain markdown editor and on another machine. `lib/core/assets.ts` owns it; `rewriteAssetSrc` (`lib/view/markdown-assets.ts`) maps the reference to `GET /api/assets/<name>` at render time and returns null for everything else, so a `data:` URI can never bury megabytes of base64 in a `.md` file.
  The serve route takes **one filename segment, never a catch-all**: an asset name contains no directories, so traversal is not a thing to defend against. `assetNameOk` is the security boundary and is pure, with the harshest test battery in the repo — it rejects `..`, slashes, drive letters, UNC and `\\?\` paths, NTFS streams (`x.png:$DATA`), DOS devices (`NUL`, `COM1.png`), trailing dot or space (Win32 strips them, so `x.png.` resolves to `x.png`), and any uppercase. `readAsset` then realpaths **both** sides and compares with `path.relative` — never a string prefix, which on Win32 is a casing coin-flip — and `lstat`s to reject anything that is not a regular file.
  **No SVG**, deliberately: served same-origin it executes inline script, which on a local-first app holding API keys is session-equivalent XSS. Diagrams are mermaid instead. The extension comes from a magic-byte sniff of the first 12 bytes, never from the upload's filename or declared type. 2 MB cap. Writes go through `withDataLock` → journal → commit like everything else, and identical bytes dedupe to one file — which matters because `commitData` does `git add -A` and git never forgets a blob.
  Ways in: paste or drop into the note editor, and the `attach_image` MCP tool (in `WRITE_TOOLS`, so `PLANNER_MCP_READONLY` gates it), which reads a path on the agent's own filesystem and appends the markdown to a note.
- Journal: `journal/YYYY-MM-DD.md`, appended lines `- HH:mm [project] message`
- Completed work is never pruned — done tasks stay in `## Done` forever. `/done` (`lib/view/done.ts`) groups them into this week / last week / earlier from `doneDate`, with an opt-in toggle that folds in done tasks from archived charters; each charter page carries a collapsed `DONE` disclosure.
- Full contract: `CLAUDE.md` in the `planner-data` repo

## Conventions

- Next.js 15 App Router; server components by default, `"use client"` only when needed
- TypeScript strict; no `any` without a reason
- Tailwind for all styling; no CSS files, no CSS-in-JS
- No code comments unless explicitly requested
- Before adding any dependency, check `package.json` and prefer what is already there
- Approved libraries: `ai` (Vercel AI SDK), `@ai-sdk/anthropic`, `@ai-sdk/openai-compatible`, `@anthropic-ai/claude-agent-sdk`, `recharts`, `gray-matter`, `simple-git`, `vitest`, `@modelcontextprotocol/sdk`, `tsx`, `mermaid`
- Components: small, one purpose per file; page-specific components colocated under `app/<route>/`
- A task opens as a **page**, not a dialog: `/projects/<slug>/tasks/<task-id>` and `/areas/<slug>/tasks/<task-id>`, subtasks included (`.../tasks/T-007.2`). `lib/view/task.ts` resolves one from `ws.cards` by reading the root id out of the dotted id, so a subtask is linkable without a card of its own. Every card click still goes through `openCard` in `shell.tsx`, which now navigates and stamps `?from=<current path>`; the page's back link uses that, falling back to the charter. `safeBackPath` rejects anything not starting with a single `/`, since `from` is attacker-controllable in a pasted URL. Dialogs remain for the composer only.
- **A task id is always a link to that task.** `TaskIdLink` (`components/momentum/task-id.tsx`) renders it wherever an id is shown, and a bare `T-003` written in a task plan is linkified by `linkifyTaskRefs` (`lib/view/task-refs.ts`) — but only for ids that exist in that charter, and never inside code, since a plan usually quotes a raw task line as a *sample*. An unresolvable id is left as plain text, exactly like a dangling `[[K-404]]`. Ids with no page to open — archived tasks, and proposal rows for tasks that do not exist yet — stay plain. `Markdown` sends in-app hrefs through `next/link` in the same tab and only external ones to a new tab.
- **Canvas** (`/canvas`): notes as cards on a pannable, zoomable surface, read at three depths — canvas → popup → full page. Positions live in `canvas/knowledge.md` (global, because notes do not archive with a charter and a note's scope is a list); per-charter surfaces will live at `projects/<slug>/system.md` and `projects/<slug>/canvas.md`, inside the charter directory so `archiveCharter` carries them along like `details/`. Grammar is `- <ref> | x:0 | y:0` under `## Nodes` and `- A > B | kind:requires` under `## Edges`; a node has no id of its own (it *is* the note or task) and an edge is keyed by the `(from, kind, to)` triple, so duplicates are impossible without minting ids two processes would race on. `parseCanvas` is **total — it never throws** and round-trips anything it does not understand, because this file is machine-written, touched by two processes, and only records where cards sit; contrast `parseTasks`, where a mis-parse must stop the world. Stale refs are surfaced as `orphans` and only removed by an explicit `pruneCanvas`. Every writer re-reads **inside** `withDataLock` and merges by ref, or a concurrent MCP write would be clobbered; drags are client-side and flush as one batch, so a gesture costs one commit, not one per pixel. Geometry lives in the pure `lib/view/canvas-layout.ts` (`autoLayout` is deterministic and only ever places *unsaved* nodes, so a saved position always wins) because the client engine cannot be unit-tested here. Three surfaces share one engine: `/canvas` (all notes, banded by charter), `/canvas/<type>/<slug>/system` (a charter's notes as **components**, with hand-drawn `requires`/`triggers` arrows and a delegate control), and `/canvas/<type>/<slug>` (tasks grouped by milestone, arrows derived from the subtask tree and `waits:`).
- **A charter map has a centre.** `group:core` is the charter's own `## Why` and `## MVP scope`, rendered as a card by `buildCoreNode` — no new record and nothing to keep in sync, since both are already edited on the charter page. It is a `group:` ref because the grammar already accepts one, `pruneCanvas` already refuses to delete it and orphan detection already skips it; a new ref kind would have earned none of that. Only **roots** are wired to it — a card something else already points at is reached through that arrow, so joining it to the core too would draw a starburst over the structure. Charter maps use `packAround` rather than `autoLayout`: claims are size-aware over a **signed** lattice (`cellsCovered`), because `snapToSlot` marks one cell per card regardless of size and clamps negatives to zero — in a hub layout that buries the core under every card in the left and top hemisphere. Same contract either way: entries only for unsaved ids, sorted by `(order, id)`.
- **The canvas is a tabbed workspace.** Every canvas screen carries a strip of tabs — `All notes` plus one per charter — because a charter's map was previously only reachable from the charter page. `lib/view/canvas-tabs.ts` owns all of it and is pure: `activeTabKey` and `modeOf` read the surface off the pathname, and `hrefOf` keeps you on the **same kind** of surface, so clicking another project from a task map lands on that project's task map rather than silently switching you to its system map. `applyTabOrder` is total in the way that matters — an unknown stored key is dropped and a charter the stored order has never seen is appended rather than vanishing, so creating or archiving a charter can never corrupt the strip. **Tab order and the last-open surface live in `localStorage`, not the data repo**: the last tab changes on every navigation, and committing that would bury the journal for a per-browser convenience no other machine can use. They are read through `useSyncExternalStore` (`components/momentum/use-stored.ts`), which has a server snapshot built in — the `useState`-plus-`useEffect` version is both a lint error here and a deliberate first render with the wrong value. The sidebar's Canvas link reopens the remembered surface, validated by `safeCanvasPath` because a stored `//host` would otherwise be a protocol-relative URL out of the app.
- **Knowledge and tasks are two surfaces, and the switch says so.** They always were two URLs, but which one a tab opened was *inferred* by `modeOf` from the path you arrived from, so from `/canvas` every charter tab silently opened its notes map and no control existed to say otherwise. `modeSwitch` turns that inference into two buttons. Its contract is that `href` is **null when there is nowhere to go** — the current surface, and the global board's task view, which does not exist: tasks belong to a charter, and a board of every task in the repo is the Board. That option still renders, disabled, rather than the strip changing shape depending on where you stand.
- **A topic is an area, and `/canvas` reads the whole base by status.** `lib/view/canvas-filter.ts` owns band order and filtering, and both are pure. Band order is the *whole* mechanism by which `autoLayout` groups: it lays bands out in **first-appearance order**, so ranking the notes is the only lever, which is why `bandCompare` sorts *ahead* of `buildNoteCanvas`'s id tiebreak rather than after it — after it, it does nothing. Three things are deliberate. **Filtering runs on the server**, before the model is built: the band rectangles and the viewport bounds are computed from the note list, so a client-side filter would leave every band drawn around cards no longer in it — which is also why a filtered board has a URL you can keep. **Facet counts are over the whole base, never the filtered set**, or narrowing would make every remaining option read as empty and leave no way back; a live charter with no notes is offered as a topic at zero, since a topic you have just created is the one you want to file into. And a scope naming **no live charter** gets status `none` alongside the truly unfiled, rather than being dropped the moment a status filter is switched on — `parseCanvasFilter` is total in the manner of `parseCanvas`, so a hand-typed query narrows wrongly at worst. A **topic is an area charter**, not a new record type: a note scoped to one bands here, auto-loads into chat context, reaches the MCP tools and gets a `/docs` page, all of which a third grouping concept beside charters and tags would have had to earn separately. `+ TOPIC` on the filter bar posts to the existing `POST /api/areas`, so it needed no new route — and an area needs a Why, so the form asks for one rather than minting a charter with a name and nothing behind it. One consequence to know: saved card positions are absolute, so a filter never moves a card you placed, but the *auto* position of an unplaced card depends on which bands are showing above it. A filter is a view, and unplaced cards move within one.
- **Arrows are rationed, because every `[[K-nnn]]` is one.** A board where each note cites two others draws a line for every cross-reference, and the structure disappears under it — a 15-card map measured 29 arrows. Two rules keep it legible. **One relationship is one arrow**: derived link edges dedupe on the *unordered* pair, so two notes that cite each other get a single line rather than two overlaid with opposite heads; a hand-drawn `rel` over an existing link is still suppressed, while `requires` and `triggers` survive, since they claim more than a mention does. And **at rest the board shows only its spine** — hand-drawn edges and the core's spokes. A card's own links appear while the pointer is on it, and ARRANGE shows the whole graph for editing. Prefer letting the note text carry a relationship over drawing an edge for it: the link is the record, the arrow is a view of it, and drawing both is how the soup starts. `CORE_REF` lives in `canvas-layout.ts` rather than `canvas.ts` because the client imports it as a **value**: `lib/view/canvas` reaches `lib/core`, so a value import from it drags `simple-git` into the browser bundle and fails the build, where the type-only import beside it is erased.
- **Cards resize, and grow into what they hold.** `cardTier(w, h, k)` in `lib/view/canvas-card.ts` picks chip / summary / body from the stored size **and the zoom**, so an enlarged card collapses back to a chip when you zoom out. `CHIP_SCALE` is deliberately kept clear of the zoom levels FIT produces: at 0.55 a board that fitted to 54% showed nothing but titles while the same board at 64% showed every summary, so the map appeared to change design between loads on nothing but window width. Never measure to decide this: inside the canvas transform `getBoundingClientRect` reports scaled pixels and the answer feeds back into itself. A body-tier card renders real markdown and scrolls; only those swallow the pointer (`[data-card-scroll]`), since marking every card would cost both dragging to arrange and dragging the background to pan. Sizes flush through the existing `PATCH /api/canvas` `w`/`h`, batched with position moves — a ref whose size changed still carries its x/y, because the writer merges a whole node line.
- **Double-click empty space on a charter map to create a note**, scoped to that charter and placed where the click landed. Without it a map could only ever be filled from the Knowledge page, which is why they started empty. An enlarged component card also carries its **WORK**: the tasks naming it, a row that creates one with `note:` preset, and a picker of open tasks with no component yet. Both write the task's `note:` field through the **task** route — never through `/api/canvas`, which accepts a knowledge surface where there is no charter and no `tasks.md`. No canvas edge is written for a link: the `note:` field is the only record, exactly like the derived `waits:` arrows.
- **Diagrams are mermaid fences** in a note body (````mermaid`), rendered on the note page and in the popup by `components/momentum/mermaid.tsx`. Text, so it diffs in git and the AI can write one. Two levels of laziness are both required: `next/dynamic` with `ssr: false` (mandatory — mermaid touches `document` at init, and `ssr:false` is illegal in a server component, which is why the wrapper is its own client file `markdown.tsx` merely references), *and* `import("mermaid")` **inside the effect**, since a module-level import defeats the first. `securityLevel: "strict"` is not optional: diagram text may be AI-written and can carry raw HTML labels. React re-invokes the effect, so the render id comes from `useId()` and a `dead` flag guards the result. Rendered SVG is cached by source, module-global. Canvas cards pass `diagrams={false}` and show a chip instead — thirty cards would be thirty sequential parse-and-layout passes on the main thread. `lib/view/mermaid.ts` (`isMermaidFence`, `diagramsIn`) is the pure part.
- **A component is a knowledge note that appears on a system map** — nothing marks it as one in the note itself, exactly as living in `archive/` is the only trustworthy archived signal. `note:K-020` is the eighth task field key and mirrors `target:` in every respect (shape-only validation, unknown id tolerated, serialized between `target:` and `waits:`); it is what makes `noteProgress` real and what the delegate control writes. A component is never auto-completed when its tasks finish. `list_components` exposes the graph over MCP, because an arrow meaning "camera control must exist before YOLO nano" is knowledge, and knowledge only the canvas can see is knowledge the assistant cannot use.
- **A map is writable from outside the browser.** `read_canvas`, `place_card`, `connect_cards` and `disconnect_cards` put all three canvas surfaces on the tool layer, which until now could only be arranged by dragging — so an agent could read `list_components` and never draw the arrow it had just reasoned out. One selector serves all three: no `project` is the knowledge board, and with a project `map` is `system` (the default) or `tasks`. Four things are load-bearing. The edge kind is called **`relation`, not `kind`**, because `kind` is the discriminant of `proposalActionSchema` and a field of that name would be overwritten by the spread that builds the union. The charter is resolved through `getCharter` **before** a surface is built, and the surface carries `charter.id` rather than the caller's string, which is what stops that string reaching `canvasPathFor` — it interpolates a slug straight into a file path. Both writers **re-validate what the core deliberately tolerates**: `applyMoves` and `addCanvasEdge` silently skip a ref they do not like, so without a check a typo is a successful call that wrote nothing, and a new arrow to a ref that is not on the map draws nothing visible. `disconnect_cards` checks neither ref, because removing an arrow to a note that has already been deleted is the point. And `connect_cards`/`disconnect_cards` are **proposable as well as writable while `place_card` is neither** — an arrow is a claim about structure an owner may disagree with, where a position is not, and a review row reading "moved 40px" is noise.
- **The MCP server has two transports and one implementation.** `mcp/server.ts` speaks stdio, which means the client *launches* the server, so client, checkout and data repo are necessarily on one machine. `POST /api/mcp` speaks Streamable HTTP from inside the already-running web app, so a second machine registers it with `claude mcp add --transport http planner http://<host>/api/mcp` and installs nothing. Below the transport it is the same `buildServer()`, allowlist and tool impls — `mcp/__tests__/http.test.ts` pins the HTTP tool list against `allowedToolNames`, so the two doors cannot drift. Everything that decides anything lives in **`mcp/http.ts`**, not the route: nothing under `app/` is testable, so `handleMcpRequest(req, env)` takes a web-standard `Request` and the route is a five-line shell, which is what lets the handshake, the gating and the refusals be tested by building `Request` objects with no server and no child process. Four facts to know before touching it. It is **stateless — one server per request** (`sessionIdGenerator: undefined`), because a session map is module-level state in the Next process and the `post-merge` rebuild restarts it, handing back 404s to ids issued before a deploy. **`enableJsonResponse: true` is load-bearing, not a preference**: it makes `handleRequest` resolve with a fully materialised body, which is the only reason the server can be closed in a `finally` around it — an SSE body is still being written when `finally` runs, so closing there truncates it. **`env` cannot carry a `PLANNER_DATA_DIR`**, because `dataRoot()` and every `lib/core` writer read `process.env` directly; a data root is a property of the process, never of a request, and the argument governs only the agent name, the readonly flag and the token. And the **agent name is taken from `x-planner-agent` while readonly is not** — a client naming itself can only mislabel its own trail, but one that could clear `PLANNER_MCP_READONLY` would be granting itself the write tools, so `x-planner-readonly` is honoured in the restricting direction only. Two refusals guard it: an `Origin` that does not match `Host` (a real client sends none, and this route sits on a local port where a page in the owner's browser could otherwise drive it), and, when `PLANNER_MCP_TOKEN` is set, a missing or wrong bearer token — compared with `timingSafeEqual` on equal-length buffers. Unset, the surface is as open as the web app beside it, which is right for a personal tailnet and wrong anywhere else.
- Subtasks are created from the task page's "Add a subtask" row (`parentId` on `POST .../tasks`, the same call the composer's STEPS box makes), at any depth. There is no separate subtask composer. The composer's DESCRIPTION box writes the **detail file**, not a task-line field — nobody should later "finish" the design by adding a `description:` key to the closed task grammar, which could not hold multi-line text anyway. Not every task needs splitting: a description is how you say more about one without inventing steps, and the log is how you say what happened while doing it.
- **The chat has two provider paths and they deliver tool output differently.** The AI SDK path (`app/api/chat/route.ts`) names a tool `propose_changes` and returns an **object**; the `claude-subscription` path (`lib/ai/claude-sdk.ts`) names it `mcp__planner__propose_changes` and returns a **JSON string**, because it crosses an MCP boundary. `formatTranscript` there also flattens the conversation to **text parts only — every tool call and output is dropped** — and re-sends the whole thing as one prompt each turn. Two consequences worth internalising before touching chat. **Never add a stream part type:** it must be implemented twice, the second time by hand in `mapSdkMessages`. And anything the model must *see* about an earlier proposal has to arrive as text or in the request body, because it cannot be read back out of the transcript. `lib/view/chat-parts.ts` is where the difference stops — `normaliseOutput` parses the JSON string once so no caller branches on `typeof`, and `toolNameOf` strips both prefixes.
- **A tool output renders as a card, and that is the whole generative-UI mechanism.** `components/momentum/chat/tool-cards.tsx` maps a tool name to a renderer; a tool with no entry keeps the plain `✓ name summary` chip, so the registry can never regress one it does not know. `propose_changes` was already this shape as a hardcoded branch. There is deliberately **no tool that lets the model emit arbitrary UI**: it could not be typed, could not be tested in a node environment, and would hand layout to the least reliable component in the system. Parsing lives in the pure `lib/view/chat-cards.ts` and every reader returns `null` rather than throwing — a tool result is model-adjacent data arriving mid-stream, and a card that throws takes the rail down with it.
- **A proposal is editable client-side, because apply trusts only `actions`.** `/api/proposals/apply` re-validates them against the same discriminated union and discards `title`, `summary` and `preview`, so posting an edited or filtered subset needs no backend change — that is what makes the review modal (`components/momentum/chat/proposal-review.tsx`) possible at all. Every decision is in the pure `lib/view/proposal-review.ts`. Two hazards it exists to catch: `applyProposal` **stops at the first failure with no rollback** and everything before it is already committed, so `remainderDraft` rebuilds from the per-action results and Accept resumes rather than duplicating; and a batch that creates a task *and* decomposes it **can never work**, since `decompose_task` needs an id a task created in the same batch does not have until `addTask` runs — `unresolvableRefs` blocks it before anything is written, reading `preview.scope`, which `previewRow` sets only when `findTask` actually resolved the id. For the same reason deselecting a row cannot orphan another one: nothing in a batch can reference a row the batch creates. The field descriptors in `fieldsForKind` are **hand-written, not introspected out of zod** — introspection gives no labels or ordering — and the test that builds an action from nothing but the descriptors and requires `proposalActionSchema` to accept it is what keeps them from drifting.
- **The revise payload travels in the request body, never in the message text.** `sendMessage({ text }, { body: { revise } })`; the route validates and size-caps it (`lib/ai/revise.ts`) before it is interpolated into a prompt, then passes it to `buildSystemContext`, which **both** paths call — so one edit reaches both models, and a mode instruction would not, since modes are optional and only `plan` carries the batching rule. A hidden marker inside the user's message was the obvious design and is wrong three times over: the subscription path re-sends every past user turn, so round three would carry rounds one and two's JSON for ever; `recallQuery` feeds the latest user message to knowledge search, so every revise would have searched the notes for raw JSON; and it needed stripping in three places, one server-side. On a revise turn the direct write tools are **withheld** on both paths (`toolNamesForRevise`), because prompts leak and an absent tool does not. Only the rows still ticked are sent — sending deselected ones would have the model re-propose what the user just removed, every round. Superseding is **derived from the transcript** by `resolveLineage`, not stored: the successor is a pure function of the messages, and writing it from an effect that watches the stream is what the React Compiler lint rejects.
- **A proposal is filed to disk, and `/proposals` is where it is accepted.** `propose_changes` used to build a preview and store it nowhere, so a batch proposed by the MCP server — a *separate OS process* — could never be accepted: the only Accept button lived in a chat transcript held in that browser's `localStorage`. `lib/core/proposals.ts` writes `proposals/<id>.md`; `toolImpls.proposeChanges` files it, which covers every surface at once because `app/api/chat/route.ts`, `lib/ai/claude-sdk.ts` and `mcp/planner.ts` all dispatch through `toolImplMap`. Filing is wrapped in try/catch on purpose: an agent losing its answer because an inbox write failed is worse than an unfiled proposal. The page is reachable by URL only, like `/archive/<type>/<name>`, so the rail carries a `N WAITING` chip — kept **outside** the fold, since folding away the one pointer to a URL-only page hides it exactly when an agent is most likely to have filed something. In-memory was not an option: `lib/ai/pending.ts` holds the distillation queue in a module-level singleton, which works only because that queue is filled and drained in one process.
  Three things here are load-bearing. **The preview is recomputed on every read, never stored for gating** — `previewRow` resolves a task only if it exists *at propose time*, and `unresolvableRefs` gates Accept on exactly that, so a frozen preview would keep saying "fine" for a task deleted since and the failure would land mid-batch after earlier rows had committed. **Accept claims the proposal first** (`claimProposal`, a locked `pending → applying` transition): two readers of one URL is ordinary once proposals are durable, and nothing in the write path is idempotent — `addTask` mints a fresh id every call, so a double apply duplicates rather than errors. And **`applyProposal` must never be wrapped in `withDataLock`**: it calls writers that each take the lock, which is not re-entrant, so claim and record sit on either side of it, never around it. The parser is total in the manner of `parseCanvas` and stores one action per line, so a torn write costs the line it cut rather than the batch; `JSON.parse` is guarded separately from `safeParse`, because only the first throws.
- **A routine is never a task.** `create_habit` / `create_rhythm` / `create_meal` wrap the `lib/core/daily.ts` writers that were previously reachable only from the `/daily` routes. Their absence is why the assistant used to propose a *task* reading "add the habits to /daily" — telling the user to do by hand the thing they had asked for. `create_task` likewise takes `due`, `est` and `lane` now; `addTask` always accepted them and the tool impl simply never passed them, so a dated task cost two rows on the card. **`previewRow` is exhaustive and must stay so** — it used to end in a bare `else` that treated any unrecognised kind as `update_event`, so a new action kind would have previewed as a calendar event rather than failing.
- **A check-in ends in notes and a journal line, never a transcript.** `checkin` is the fifth chat mode (`lib/ai/modes.ts`): two to four short questions, then one closing reply that files one to three durable facts with `add_note` — **scope set explicitly** to an area from the `Areas:` line the context now carries, tags `["checkin"]` — and one `add_journal` line `[life] check-in: …`. The explicit scope is what makes it work on the subscription path: `classifyNote` short-circuits to `explicit` and never needs structured output. Chat transcripts stay in the browser on purpose; what the model must remember has to be *filed*, and this mode is the procedure for filing it. The unfocused context, which is where a life conversation happens, now gets a `# Life` block — the last seven days of journal and an eight-week habit/rhythm table from `lib/core/trends.ts` — because until it did, "how has my week been?" was answered from `about.md` and today's habit count. Three caps keep the prompt bounded: `JOURNAL_LINE_CAP` (40 most recent lines, oldest first, `+N earlier`), `OPEN_TASK_CAP` (30, ordered by `rankOpenTasks` so the tasks shown are the ones `next_actions` would name), and `get_daily` hands the model 28 days of the log rather than all of it.
- **"Where does this lead" is a number before it is a sentence.** `lib/core/trends.ts` is pure over `DailyData` + `Insights`: per habit the weekly adherence, streak, `slope` (least squares over *complete* weeks, in percentage points per week — the current week is excluded and starred), `recent4` / `prior4`; per rhythm the count against target by week; task throughput and stalled charters straight from `insights.ts`. `life_trends` exposes the structure to chat and MCP (`READ_TOOLS`, so readonly agents get it), and `renderTrendsDigest` puts a ten-line version in the unfocused context. The projection itself is left to the model on purpose — the check-in instruction says *four more weeks like the last four, one sentence, then at most one habit change, numbers from the table* — because prose computed in code would be worse prose and the table is the part that must not be guessed.
- **Long conversations are windowed on the client, and the rest travels as a digest.** `windowMessages` (`lib/view/chat-window.ts`, pure) keeps the last twelve messages, trims further to a character budget, never below two, and always opens on a user message — a tool call and its result live inside one assistant message, so a cut on a message boundary never separates them. It runs inside the transport's `prepareSendMessagesRequest`, so `useChat` state and `localStorage` keep the whole transcript and only the wire payload shrinks — on **both** provider paths at once, which matters because the subscription path re-sends the transcript as text and had nowhere else to be trimmed. The digest is heuristic and deterministic (`digestOf`: first user message, tools used with their ids, last assistant text, a count) — no extra model call, identical everywhere, and it carries the ids the model must not lose. It reaches the model exactly the way `revise` does: in the request body, capped and stripped server-side by `parseDigest`, rendered into the system prompt by `buildSystemContext`'s fifth argument — never as a message, or `recallQuery` would search the notes for it and the subscription path would re-send it for ever.
- **The rail folds its own chrome once a conversation starts, and it can be dragged wider.** Scope, the four mode buttons, history and the opener line cost about 190px above the transcript — worth it while choosing how to ask, worthless while reading the answer, which is why `chromeFolded` in `lib/view/chat-layout.ts` derives the fold from `messages.length` rather than storing it. An explicit FOLD/MORE click wins, and lasts only as long as the conversation: `startSession` and `pickSession` both clear the override, so a new conversation always opens with its controls showing. Width is dragged from a handle on the rail's left edge and kept in `localStorage`, **not** the data repo — it is a per-browser convenience, and committing it would bury the journal exactly as the canvas tab order would. Two things are easy to get wrong here. The rail is anchored right, so **dragging left widens it** (`dragRailWidth` subtracts, and the sign is invisible in a diff). And `storedRailWidth` is called during render with **no viewport**, deliberately: the server and the first client render cannot measure a window and disagreeing about it is a hydration mismatch, so the CSS `max-width: 70vw` caps it until the first drag, which does know the real width. Resizing is docked-mode only — under 1280px the rail is an overlay, where a width the user cannot see the page behind is not a width worth having.

## Testing

- `lib/core` changes require tests in `lib/core/__tests__/` (vitest)
- Markdown round-trip is the highest-risk code: parse → serialize → parse must be identity
- Malformed task lines must throw clear errors, never silently corrupt

## Definition of done

`npm run lint && npm run typecheck && npm test` all green, rules above respected.

## Landing work

**Never push to `main`, and never merge into it locally. Open a pull request.**
Work on a branch, push the branch, `gh pr create`, and let the PR be reviewed
and merged — even when the change is small, even when the person asking said
"merge it". "Merge it" means land it the normal way, not skip the review step;
a merge is the one action nobody can undo once it is pushed to a public repo.

Two consequences specific to this setup:

- **A merged PR does not deploy on its own.** The live app is served from the
  main checkout by a local service, so a deploy still needs `git pull` on
  `main` there. The pull is what triggers the deploy — see below.
- **Deployment is automatic but invisible.** A `post-merge` hook rebuilds and
  restarts the service on any merge or pull into `main`. It is deliberately not
  in the repo: it holds one machine's service name and port, and this repo is
  public. It lives in `.git/hooks/post-merge`, and because `.git/hooks` is
  shared by every worktree it guards on both branch and toplevel path —
  without that, a pull inside `.claude/worktrees/*` would redeploy the live app
  from the wrong branch. It builds while the old build is still serving and
  restarts only on success, so a failed build leaves the app running.
